<objective>
Failures stop being a number and become a record, and the moment a source breaks, Discord says so —
from the collector, which is the only process awake when it happens.

**User story (MVP):** **As** the person who owns this system, **I want** a Discord message the
moment a collection run records a failure **so that** I learn about a broken source when it breaks,
not fifteen minutes later in the digest and not never.

This is the collector-side vertical slice: the per-pair except block that already computes the cause
and the message keeps them instead of discarding them, they land in a new table in the same
transaction context as the `runs` row, and one message per run goes out over the Phase 5 webhook. The
bot is not involved and holds no webhook credential; the collector is not involved in the digest and
holds no bot token. Two credentials, one channel (D-02).

Purpose: ROADMAP criterion 3 requires the failure message to be "distinct from and earlier than the
scheduled digest". Only a process that is alive at the moment of failure can be earlier, and the
collector is the only one. Persisting the detail is what lets 06-03's digest and 06-05's `/status`
report the same failures the alert named, instead of each inventing its own view.

Output: the `run_failures` table, `RunFailure`, `write_run_failures()`, `build_alert_text()`,
`_post_alert()`, and two call sites in `cli.py`.

**Decisions this plan implements, and where.** D-02 — the collector posts to the Phase 5 webhook with
`requests`, holding no bot token and acquiring none (Task 2). D-06 — the `run_failures` table with its
five columns, `write_run_row` returning the inserted id, and `collect_once` accumulating detail rather
than a count (Task 1). D-07 — any run with a non-zero failure count alerts, one rule and no cross-run
state, and a `no_fetcher_registered` skip is never a failure (Tasks 1 and 2). D-08 — one message per
run listing every failure, sent after the `runs` row commits and not from inside the per-pair except
(Task 2). D-09 — a Sheets sync failure alerts from the except block that already exists, before the
re-raise, and a failed POST is logged and swallowed rather than replacing the error in flight
(Task 2). D-20 — the formatters are tested against fixtures and no live network call enters the suite
(Task 2 tests).

**Decisions this plan deliberately implements by *not* building something.** D-07's rejected
alternative — no consecutive-day threshold, no suppression window, and no cross-run state of any kind;
three creators cannot make this channel noisy, and a threshold would suppress the single-day outage
most worth knowing about. D-06's rejected alternative — no TEXT summary column on `runs`, which would
need a hand-run `ALTER TABLE` against the live database and produce an unqueryable blob.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| external API response → exception message → Discord message | An upstream error string this project does not control is interpolated into a message Discord renders as markdown |
| environment file → collector process → outbound HTTPS | `DISCORD_WEBHOOK_URL` is a bearer credential; anyone holding it can post to the channel |
| collector → SQLite (`run_failures`) → bot | The only new data path in the phase; the collector remains the sole writer |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-03 | Information Disclosure | `_post_alert()` in `cli.py` | high | mitigate | The URL is read from the environment and passed straight to `requests.post`; no log line, no exception message, and no alert body contains it. Asserted by a `caplog` test. |
| T-06-06 | Tampering | Alert body interpolating an upstream exception message | low | mitigate | The POST body sets `allowed_mentions` with an empty `parse` list, so no interpolated text can ping the channel — the same control Phase 5's COVERAGE.md records as T-05-05. |
| T-06-07 | Denial of Service | The alert call sites inside `run_collect` | medium | mitigate | `_post_alert` uses a 10-second timeout and swallows `requests.RequestException`, so an unreachable or hanging webhook cannot stall or fail the collection run. One message per run rather than per failing pair (D-08) bounds the outbound volume at one POST regardless of how many sources break. |
| T-06-08 | Repudiation | Alert count versus the persisted `runs` row | low | mitigate | Both are built from the same `RunResult`, so the channel and the database cannot report different failure counts for the same run. Asserted by the `len(failures) == failure_count` invariant test. |
| T-06-SC | Tampering | pip installs | high | accept | This plan installs no packages — `requests` 2.34.2 is already locked and already used directly by `sources/youtube.py`. 06-RESEARCH.md's Package Legitimacy Audit records an empty table. No install step exists to gate. |
</threat_model>
