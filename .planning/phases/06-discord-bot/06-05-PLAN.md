<objective>
Make Discord the place you *ask* about the numbers, not just the place they show up.

**User story (MVP):** **As** the person who owns this system, **I want to** type `/creator kaicenat`
or `/status` in the channel and get an answer from the database **so that** I can check on a creator
or on the collector itself without opening the Sheet, SSHing to the droplet, or waiting for tomorrow
morning's digest.

**This plan is cut-order item 1 and the only cut left.** It is deliberately the last plan, nothing
depends on it, and it shares no file with 06-04, which runs in the same wave. Cutting it is one
command — delete this file — and the digest, the failure alert, the schema, and the systemd unit are
all unaffected. That is the whole point of D-14: with hours left before a live interview the cut has
to stay a decision someone makes calmly, not a scramble someone performs mid-execution. Do not add a
dependency on this plan from anywhere.

Purpose: criterion 4 names both commands, and they are the "and the place you ask about them" half of
the phase goal. `/status` also does double duty — Phase 7 criterion 2 requires it to report staleness
honestly when the run is deliberately broken, so building the verdict now means Phase 7 rehearses
rather than implements.

Output: `fetch_known_creators()`, `fetch_creator_trend()`, `build_trend_text()`,
`build_status_text()`, and the two registered commands.

**Decisions this plan implements, and where.** D-14 — BOT-04 and BOT-05 land in their own final plan
and nothing depends on it (this whole file). D-15 — `/creator <name>` matches `creator_id` exactly and
case-insensitively, with an unknown name replying with the list of known slugs (Task 1). D-16 —
"recent trend" is the last seven daily rows for that creator, date, views, and delta, from one indexed
read (Task 1). D-17 — `/status` returns the numbers plus an OK or STALE verdict at the same 26-hour
threshold as Phase 5's watchdog, naming the failing sources when there are any (Task 2). D-12 — the
same em dash and the same NULL-versus-0 rule the digest uses (both tasks). D-20 — the formatters are
tested against a temporary database and the command callbacks are not, by design (both tasks).

**Decisions this plan deliberately implements by *not* building something.** D-15's rejected
alternatives — no `app_commands` autocomplete, which would add a Discord API surface to explain and
fire a database read per keystroke, and no substring or fuzzy matching, which would need an ambiguity
rule this project has no reason to defend. Both are recorded as deferred ideas, not oversights.
</objective>

    **`src/creatorpulse/db.py`** — add two reads in the file's existing style.

    `KNOWN_CREATORS_SQL` selects the distinct `creator_id` values from `metrics`, ordered, and
    `fetch_known_creators(conn)` returns them as a list of strings. The list comes from the database
    rather than from `creators.yaml`, matching Phase 4 D-01's rule that the surfaces are built from
    what was collected, not what was configured; a creator added to the config this morning is
    genuinely not yet answerable and saying so is honest.

    `CREATOR_TREND_SQL` selects source, `metric_date`, and `views` from `metrics` where `creator_id`
    matches, ordered by source then `metric_date` descending, and `fetch_creator_trend(conn,
    creator_id)` executes it. The creator id is passed in the **parameter sequence against a `?`
    placeholder** — this is the one query in the whole codebase whose input comes from a stranger
    typing in a Discord channel, and it is bound for exactly that reason (threat T-06-01).

    A note on the deviation from D-16's literal mechanism, which should be a comment on the constant:
    D-16 named "one indexed read with `LIMIT 7`". A flat `LIMIT 7` is correct only while a creator has
    exactly one source, and `creators.yaml` already declares `twitch` and `tiktok` entries that will
    start producing rows the moment either is registered — at which point a flat limit silently
    interleaves two sources into three and a half days each. The read stays one indexed pass against
    `idx_metrics_creator_date` and the outcome D-16 specifies is unchanged; the seven-row cut is
    applied per source in `build_trend_text` instead of in the SQL. D-16 is a Claude's-discretion
    decision and the mechanism is explicitly the implementer's.

    **`src/creatorpulse/bot.py`** — add `TREND_LIMIT = 7`.

    Add `build_trend_text(conn, name)`, pure and fixture-testable. It normalises the input with
    `.strip().lower()` and compares it against the values from `fetch_known_creators`. Use
    `str.lower()` rather than `str.casefold()`, and say why in a comment: `config._SLUG_RE` constrains
    every `creator_id` to lowercase ASCII letters, digits, and hyphens, so simple lowering is an exact
    inverse over that alphabet, whereas `casefold` would introduce Unicode folding behaviour with no
    id it could ever match. No substring matching, no fuzzy matching, no autocomplete — there is no
    ambiguity rule to defend for three creators with distinct names, and no path by which the bot
    quietly answers about the wrong one (D-15).

    On a miss it returns a reply naming what was typed and listing the known slugs; when that list is
    empty it says the database holds no creators yet instead of trailing off after a colon. On a hit
    it groups the returned rows by source, takes the first `TREND_LIMIT` of each — the query already
    ordered newest first — and renders one block per source: a heading line with the creator and
    source, then one line per day reading date, views, and delta. Views render blank when NULL and as
    the number when 0, the same NULL-versus-0 rule `build_dashboard_rows` already applies. The delta
    on each line is that day's views minus the next older row's views, and it renders
    `sheets.DELTA_PLACEHOLDER` whenever either side is NULL or the older row does not exist — so the
    oldest line shown always carries the em dash, and a single-day creator's one line does too. A
    first row is not a zero move.

    Register the command on the bot's tree with the name `creator`, a description, and one string
    parameter with its own description. The handler opens `db.connect(db_path, create=False)`, calls
    `build_trend_text` inside a `try/finally` that always closes the connection, and replies with
    `interaction.response.send_message(text, allowed_mentions=discord.AllowedMentions.none())`. No
    `defer()` — a single indexed read over a database this size finishes in low single-digit
    milliseconds, comfortably inside Discord's three-second initial-response window, and deferring
    would add a second round trip for nothing (06-RESEARCH Priority 4). No module-level connection.

    **Tests** in `tests/test_bot.py` and `tests/test_db.py` cover every case in the `<behavior>`
    block, verbose one-behavior-per-test names, seeded with `upsert_metric` against a `tmp_path`
    database. Do not import or mock discord.py — the command callback is untested by design (D-20)
    and the formatter is what carries the behaviour.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Discord guild member → `/creator <name>` → SQL | The only place in this system where a value typed by a person reaches a database query. Anyone in the guild can type anything. |
| SQLite → command reply → Discord channel | Row values are interpolated into a message Discord renders as markdown and shows to everyone in the channel |
| bot process credentials → command reply | An unhandled error inside a handler could, if written carelessly, echo configuration into a public channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Tampering | The `/creator` name lookup in `db.fetch_creator_trend` | high | mitigate | The name is lower-cased and passed in the parameter sequence against a `?` placeholder; the SQL constant is a fixed string with no interpolation. Asserted by an acceptance criterion that scans `db.py` for an f-string query. This is the single highest-value control in the plan — every other query in this codebase already follows it and this one takes untrusted input. |
| T-06-04 | Denial of Service | Command handlers running on the gateway event loop | medium | mitigate | Each handler opens a short-lived connection, runs one indexed read, and closes it in a `finally`. No module-level connection can leak across handlers and no unbounded query exists — the trend read is scoped to one creator and rendered at seven rows per source. `defer()` is deliberately not used because the read finishes well inside the three-second window. |
| T-06-02 | Information Disclosure | Replies sent by either command | high | mitigate | Both replies are built only from database rows by pure functions that receive no configuration. `DatabaseNotInitialized` propagates rather than being formatted into a reply, so no path exists by which a resolved path or credential is echoed into a public channel. |
| T-06-06 | Tampering | `creator_id` and failure text rendered into a reply | low | mitigate | Both replies pass `AllowedMentions.none()`, so no value read out of the database can ping the channel. |
| T-06-11 | Elevation of Privilege | Command visibility inside the guild | low | accept | Both commands are readable to anyone in the one guild the bot is invited to, and no per-user authorization exists. Accepted: this is a single-operator project with authentication, multi-user, and roles explicitly out of scope, and neither command exposes anything beyond public creator metrics and the collector's own run statistics. Discord's guild-membership boundary is the access control. |
| T-06-SC | Tampering | pip installs | high | accept | This plan installs no packages. 06-RESEARCH.md's Package Legitimacy Audit records an empty table for the phase. |
</threat_model>
