<objective>
Finish the digest. The tracer proved a message can be built and sent; this plan makes that message
say the three things BOT-01 and BOT-02 actually require — which creator moved enough to care about,
whether the numbers can be trusted at all, and what broke during the run that produced them.

**User story (MVP):** **As** the person who owns this system, **I want** the morning digest to flag
the creators who moved more than ±20%, tell me when the numbers are stale, and list what failed
**so that** one message answers "is anything interesting, and can I believe it" without opening the
Sheet.

Every change lands inside `build_digest_text(conn, now)`, whose signature 06-01 deliberately fixed
so this plan adds reads and lines rather than reshaping a function its tests already cover.

Final digest shape:

```
CreatorPulse digest — 2026-08-06
⚠ last run finished 2026-08-04T00:00:12+00:00 — STALE (54h ago)
🚨 kaicenat / youtube — 1,234,567 views (Δ +250,000, +25.4%)
   pokimane / youtube — 987,654 views (Δ -1,200, -0.1%)
   xqc / youtube — 555,000 views (Δ —)
Failures this run: 1
   mkbhd / youtube — ChannelNotFound: no channel for handle @mkbhd-typo
```

The banner line appears only when the run is stale or undeterminable; on a healthy day the message
opens straight into the movers.

Purpose: BOT-02's threshold is the phase's one numeric contract and it is stated as *exceeds* ±20%,
which makes exactly ±20% a boundary that has to be decided rather than discovered. D-04's banner is
the same refusal-to-be-silent that Phases 3, 4, and 5 each applied at their own boundary, and it
shares its threshold constant with `/status` so the two cannot drift.

Output: `FLAG_THRESHOLD`, `MOVER_FLAG`, `staleness_hours()`, `fetch_last_run()`,
`fetch_run_failures()`, and a `build_digest_text` that renders all three sections.

**Decisions this plan implements, and where.** D-04 — on a stale day the digest posts anyway, led by
a banner, and the off-box watchdog is explicitly not made redundant by it (Task 1). D-10 — the flag is
decided on the percent, and both the absolute figure and the percent stay visible beside it (Task 1).
D-11 — the ordering stays every row by absolute percent descending, with no cap introduced (Task 1).
D-12 — no baseline and a zero baseline both render the shared placeholder and neither can be flagged
(Task 1). D-17 — the 26-hour threshold lives in one constant that this banner and `/status` both read
(Task 1). D-06 — the digest lists that run's failures from the table 06-02 created (Task 2). D-20 —
the banner, the flag, and the failures block are all pure-formatter behaviour tested against a
temporary database (both tasks).

**Decisions this plan deliberately implements by *not* building something.** D-04's rejected
alternative — the digest never stays silent on a stale day and never defers to the 09:00 watchdog;
silence is indistinguishable from the digest not having fired. D-11's rejected alternative — no top-N
cap; a cap that never triggers at three to six rows is untested code that has to be explained.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `run_failures.message` → digest text → Discord channel | An exception string originating in an upstream API is interpolated into a rendered message |
| stored run id → SQL read | An integer read out of the database is used to select rows; a formatted query here would establish the habit that 06-05's user-supplied `/creator` name then inherits |
| digest tick → gateway | Every read this plan adds executes inside the task-loop body, where an unguarded exception would end all future digests |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Tampering | `fetch_run_failures` in `db.py` | high | mitigate | The run id is bound as a parameter with a `?` placeholder, never interpolated. This is the query whose shape 06-05's `/creator` lookup copies, so the discipline is established here on a trusted value before it is applied to an untrusted one. |
| T-06-04 | Denial of Service | The two new reads inside the digest tick | high | mitigate | Both execute inside `digest_loop`'s existing broad guard; no new try/except is added and nothing re-raises out of the decorated coroutine. A malformed row therefore costs one log line and one missed digest, never every future digest. |
| T-06-06 | Tampering | Failure `message` and `cause` rendered into the digest | low | mitigate | `channel.send` already carries `AllowedMentions.none()` from 06-01, so an upstream error string containing an at-mention cannot ping the channel. |
| T-06-09 | Repudiation | The staleness verdict versus Phase 5's watchdog | medium | mitigate | Both use 26 hours and both use a strict greater-than, so the same moment is never reported stale by one surface and fresh by the other. | T-06-SC | Tampering | pip installs | high | accept | This plan installs no packages. 06-RESEARCH.md's Package Legitimacy Audit records an empty table for the phase. No install step exists to gate. |
