<objective>
Prove the whole Phase 6 architecture on one path: environment variables in, a long-lived bot
process connected to the Discord gateway, a short-lived read of the real SQLite database, and one
real digest message landing in the real channel. Everything after this plan expands out from a slice
that already works.

**User story (MVP):** **As** the person who owns this system, **I want to** see one real digest
message land in the Discord channel from the bot's own process **so that** the architecture the rest
of the phase builds on — config, gateway, task loop, database read, formatter — is proven end to end
before any of it is expanded.

The plan opens with the D-13 refactor because it moves a query out of a finished, verified module
and is the one `costly` decision in the phase. It is committed alone, with the four-command gate run
immediately after, so a breakage is isolated to a commit that does nothing else. It is a
prerequisite, not a layer of the slice; the tracer is Task 2.

Digest message shape (pinned here so every later plan formats the same way):

```
CreatorPulse digest — 2026-08-06
kaicenat / youtube — 1,234,567 views (Δ +250,000, +25.4%)
pokimane / youtube — 987,654 views (Δ -1,200, -0.1%)
xqc / youtube — 555,000 views (Δ —)
```

The staleness banner (D-04), the ±20% flag (D-02/BOT-02), and the trailing failures block (BOT-01)
are added by 06-03 against the same function, without changing its signature.

Purpose: the riskiest thing in this phase is not any single formatter — it is whether a second
long-lived process, its config, its gateway connection, and its scheduled loop hang together at all.
Answer that first, on the agent's best tokens.

Output: `src/creatorpulse/bot.py`, `resolve_discord_config()` in `config.py`, a real `creatorpulse
bot` subcommand, `tests/test_bot.py`, and the D-13 move.

**Decisions this plan implements, and where.** D-01 — the digest fires from the bot's own
`discord.ext.tasks` loop, not from the collector and not from a second timer (Task 2). D-02 — the bot
posts with its bot token over the already-connected gateway; the webhook belongs to the collector and
is 06-02's (Task 2). D-03 — 08:15 Asia/Manila, fifteen minutes after the collector and forty-five
before the off-box watchdog (Task 2). D-10 — percent computed in the bot, both the absolute figure
and the percent displayed (Task 2). D-11 — every row, sorted by absolute percent descending, no
top-N cap (Task 2). D-12 — no baseline or a zero baseline renders the shared placeholder (Task 2).
D-13 — the query moves, first and alone (Task 1). D-19 — config fails loudly, by name, before
anything connects (Task 2). D-20 — the pure formatters are tested and the gateway, the loop, and
command registration are not, by design and in writing (Task 2 tests).

**Decisions this plan deliberately implements by *not* building something.** D-05 — there is no
catch-up digest. A bot restarted at 09:30 waits for tomorrow; it does not notice it missed today, and
no "already posted today" marker, no persisted state, and no restart-loop suppression may be added to
change that. The gap is covered three other ways — the Sheet holds the numbers, `/status` reports
staleness on demand, and the off-box watchdog is watching — and adding state to close it is the trade
this project keeps declining. D-21 — `deploy/creatorpulse-bot.service` was already written and
committed under a dated, scoped exception, and no task here reopens, edits, or installs it.

**Decisions already discharged before this plan, recorded so nobody re-does them.** D-18's
`.env.example` half — all four Discord variable names already exist in `.env.example` with blank
values, landed by quick task `260806-k5w` on 2026-08-06. Do not add them again and do not put a value
next to one. What remains of D-18 in this plan is only the reader: both processes take the four names
from the same `/etc/creatorpulse/creatorpulse.env` the collector already reads.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| environment file → bot process | `DISCORD_BOT_TOKEN` and `DISCORD_WEBHOOK_URL` are bearer credentials crossing from a `chmod 600` file into process memory and, if handled carelessly, into the journal |
| bot process → Discord gateway | The bot authenticates and then holds a long-lived connection carrying whatever privileges the guild role and the requested intents grant |
| SQLite → digest text → Discord channel | Row values (creator ids, exception-derived text later) are interpolated into a message Discord renders as markdown |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-02 | Information Disclosure | `resolve_discord_config()`, `DiscordConfigError`, every log line in `bot.py` | high | mitigate | Error text and log records name the variable, never the value; the token goes straight from the dataclass into `client.run()` and is never logged or formatted into a message. Asserted by the `-k config` tests. |
| T-06-04 | Denial of Service | `digest_loop` body in `bot.py` | high | mitigate | The entire loop body is wrapped in `try/except Exception: logger.exception`. Without it a single non-network exception kills the loop's Task permanently while the unit stays green — a silent, symptomless outage. Asserted syntactically in the acceptance criteria. |
| T-06-05 | Elevation of Privilege | Requested gateway intents and the bot's guild role | medium | transfer | Code requests `discord.Intents.default()` and nothing else — no privileged intent. No code path can compensate for an overprivileged invite. |
| T-06-06 | Tampering | Digest text sent via `channel.send()` | low | mitigate | `allowed_mentions=discord.AllowedMentions.none()` on every send, so no interpolated value can ping the channel. Follows the `allowed_mentions: {parse: []}` precedent recorded in Phase 5's COVERAGE.md (T-05-05). |
