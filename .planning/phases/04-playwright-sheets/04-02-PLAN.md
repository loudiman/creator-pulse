number: strict day-over-day on `views`, baselined against `metric_date - 1 day` exactly, computed in
Python from two nullable integers that arrive in the same single indexed read.

Purpose: this is the only column on the Dashboard that is *derived* rather than copied, so it is the
only one that can be wrong while looking right. Every other cell is a value the database already
holds — if it is wrong, the collector is wrong. Column E is arithmetic over two rows that may not both

plan exists to pin down, and why it lands as its own plan rather than as a line inside the tracer.

**`LATEST_ROWS_SQL`.** Keep the existing `FROM metrics AS m` and the existing correlated
`WHERE m.metric_date = (SELECT MAX(m2.metric_date) ...)` subquery exactly as `04-01` wrote them,
including its comment. Add one thing: a **left** outer join to a second alias of `metrics` — name it

The join must be a **left** outer join and this is load-bearing, not stylistic. An inner join would
silently delete from the Dashboard every pair that has no previous-day row — which is every creator on
its first day, and every creator on the day after a missed run. The row count would still look
plausible, the ops team would see a shorter table, and nothing in the green gate would notice. This is
the one place in this plan where the wrong keyword produces missing rows rather than wrong numbers.
