## Phase Goal

> The Sheet stops being a dump and becomes a two-way surface — it formats itself and talks back to Discord.

*(Reproduced verbatim from ROADMAP. Not in user-story form; see 05-01's note.)*

<objective>
The expansion. 05-01 proved the whole architecture on one path — menu, installable trigger, event
object, Script Properties, webhook. This plan builds outward from that proven slice into the two
capabilities that make the Sheet a *surface* rather than a notifier: it formats itself (SCRIPT-04)
and it watches itself (SCRIPT-02).

Purpose: after 05-01 a human edit produces a Discord message. After this plan the Sheet also colours
its own day-over-day movement, and a collector that has stopped running says so — from Google's
infrastructure, which is the one place in this system that survives the failure it is watching for.

and the outage produces silence rather than an alert. That structural argument is D-05's whole
content and it is the interview answer, so the code has to actually carry it.

Output: `checkFreshness()`, `applyFormatting()`, the daily time-driven trigger, and the two remaining
menu items — appended to the file 05-01 created.

**This plan is blocked on an empirical answer, not on a preference.** RESEARCH.md Pitfall 4:
Python writes column F as an ISO-8601 string with a `+00:00` offset and gspread writes it with
`USER_ENTERED`, so the cell may hold a real `Date` or plain text. 05-01's `_diagnoseTimestampType()`
answers which. Getting it wrong fails in the dangerous direction: a `NaN` comparison makes
`NaN > threshold` false, so the watchdog never fires, and under D-07's "silent unless broken" a
watchdog that never fires is indistinguishable from a healthy day. That is the worst available
outcome and it defeats the entire reason D-05 exists.

**Not in this plan:** any Python, any new file, any change to the Dashboard's column layout or tab
name, and every idea in 05-CONTEXT.md §Deferred Ideas — the column-G dropdown, the stale-row format
rule keyed on column F, the daily heartbeat, and a second webhook. `COVERAGE.md`, `05-UAT.md`, and
the criterion-5 walkthrough are 05-03's.

## Verified Apps Script facts (RESEARCH.md, checked against primary docs — do not re-derive)

1. **`setConditionalFormatRules(rules)` REPLACES the sheet's whole rule array. It does not merge.**
   Reading the existing rules, pushing onto them, and writing the grown array back doubles the rule
   count on every click. Build a fresh two-element array each time.
2. **Number-comparison rules do not evaluate non-numeric cells.** A text cell — which is what the
   em-dash placeholder is — satisfies neither `whenNumberGreaterThan(0)` nor `whenNumberLessThan(0)`,
   and the rule is skipped for that cell without erroring and without treating text as zero.
   `[ASSUMED — HIGH practical confidence]`: this is standard Sheets behaviour applied identically
   through the API, but no source states the em-dash case specifically. It is visually obvious if
   wrong (a coloured `—` cell) and the fallback is a one-line custom-formula exclusion.
3. **`atHour(9)` means "sometime in the 09:00–10:00 window", not exactly on the hour.** Google's
   docs are explicit that time-driven triggers fire inside an hour-wide window. Nothing in D-06
   depends on minute precision.
4. **The manifest `timeZone` and the builder's `.inTimezone(...)` are two settings, not one.**
   `.inTimezone()` is what actually pins `atHour()` to Manila local time; the manifest is the
   fallback used when `.inTimezone()` is omitted. Both are set to `Asia/Manila` deliberately —
   redundant and correct.
5. **`Date.now()` and `getTime()` are both epoch milliseconds**, so the age arithmetic is a plain
   subtraction divided by 3 600 000. No timezone conversion belongs anywhere in the comparison — a
   UTC instant minus a UTC instant is a duration regardless of how either is displayed.

**`checkFreshness()`** — the watchdog body, called by both the time-driven trigger and the menu item.
Three outcomes and exactly three, in this order:

1. **Cannot determine.** `SpreadsheetApp.getActive().getSheetByName(DASHBOARD_TAB)` returns nothing;
   or `sheet.getLastRow()` is below `FIRST_DATA_ROW` (a header-only tab); or every cell scanned in
   column F is blank or fails to parse. Each posts a **distinct** alert saying the watchdog could
   not determine freshness and naming which of the three it hit.
2. **Stale.** The newest parseable timestamp is more than `STALE_THRESHOLD_HOURS` old. Post an alert
   naming that timestamp — as an ISO-8601 string so it is unambiguous — and the age rounded to whole
   hours.
3. **Fresh.** Return without posting anything.

**Outcome 1 is a deliberate departure from RESEARCH.md's illustrative example, and it is the most
important line in this plan.** That example returns silently when nothing parses, on the reasoning
that a parse failure should not be reported *as staleness*. The first half is right and is kept —
the message must not claim the collector is stale when the truth is that the watchdog cannot read
the column. The second half is wrong for this project: D-07 makes silence carry exactly one meaning,
"the data is fresh", so a silent return on a parse failure hands the watchdog a second, invisible
meaning and reproduces PITFALLS.md §18(d) inside the very thing built to answer it. This project's
convention is fail loudly and name the fix (Phase 3 D-16, Phase 4 D-07, `sheets.py`'s
`SheetsKeyfileUnusable`), and it applies here. Distinct message, never silence, never a false
staleness claim.

The scan, between outcomes 1 and 2: read column F for the data rows in **one** `getRange(...)
.getValues()` call — first row `FIRST_DATA_ROW`, first column `LAST_UPDATED_COLUMN`, height
`lastRow - FIRST_DATA_ROW + 1`, width 1. One range read, not a per-row `getValue()`; the same
batching judgment SHEET-05 applies on the Python side applies here for the same reason. Then walk
the returned rows tracking the largest epoch milliseconds seen, starting from a `null` sentinel:

- Skip a cell that is blank, `null`, or `undefined` — an empty column F cell is not a parse failure,
  it is an absent row, and only *all* of them being unusable is outcome 1.
- Convert with the branch the Wave 0 answer selects, written to survive either: use the value
  directly when it is `instanceof Date`, otherwise pass it to `new Date(...)`. Keeping both arms
  costs one ternary and means a future change to `value_input_option` on the Python side cannot
  silently break this.
- Take `.getTime()` and **discard the candidate when it is `NaN`**, before it can enter the
  comparison. This guard is the one that matters: `NaN` propagates through arithmetic, and
  `NaN > STALE_THRESHOLD_HOURS` evaluates false, so a single unguarded `NaN` winning the newest
  comparison makes the watchdog permanently, invisibly silent. Guard at the point of parsing, not at
  the point of comparison.
- Keep the larger of the candidate and the running maximum. No tie-break is needed and none should
  be written: two rows tying for newest carry the same instant, so the reported value is identical
  whichever wins and the result cannot depend on row order.

Then age in hours is `(Date.now() - newest) / 3600000` — epoch milliseconds on both sides, a
duration, no timezone conversion anywhere. Compare with a **strict** `>`: an age of exactly 26.0
hours stays silent. That is the tolerant direction and it is the right one for a threshold chosen to
absorb a slow run rather than to catch one; say so in a comment so the strictness reads as a choice.
