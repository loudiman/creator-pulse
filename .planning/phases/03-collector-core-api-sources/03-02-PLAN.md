**`models.py`.** Two frozen slots dataclasses matching `Creator`'s decorator form exactly:
`MetricRecord` with the nine fields in the interface contract above, and `RunResult` with
`rows_written` and `failure_count`. No validation logic inside either dataclass — `Creator` sets that
convention. Every metric field is `int | None` explicitly; mypy `strict = true` is what forces the
NULL case to be handled as real code rather than assumed away. `is_live` is `int | None`, not
`bool | None`, so the Python type matches the declared INTEGER column and the field lines up with
its siblings. One-line module docstring, `config.py` style.

**`db.py`.** Module docstring: one line, the only module in the package that touches SQL.
`SCHEMA_DDL` is the verified block from RESEARCH.md §"DDL and upsert" — `metrics` with the nine
columns and `UNIQUE (creator_id, source, metric_date)`, the `idx_metrics_creator_date` index, and
`runs` with `id INTEGER PRIMARY KEY AUTOINCREMENT, started_at, finished_at, rows_written,
failure_count`. `metric_date` and `collected_at` are TEXT holding ISO-8601; the four metric columns
are nullable INTEGER and the comment beside `followers` states that NULL means the platform does not
expose the metric. `runs` carries no uniqueness constraint — it is append-only, and two runs on one
date are two rows. There is no `duration` column: DATA-03's duration is `finished_at - started_at`,
and storing a derived value that could disagree with its inputs is worse than computing it.

`connect(db_path: Path, *, create: bool)`: this task implements the `create=True` branch only
(`sqlite3.connect(str(db_path), timeout=5.0)` then `executescript(SCHEMA_DDL)`); leave the
`create=False` branch for 03-05 by raising `NotImplementedError` with a message naming 03-05, so the
gap is loud rather than silently wrong. Set `PRAGMA journal_mode = WAL` and
`PRAGMA busy_timeout = 5000` on **every** connection, before the branch, both flags, every time —
this is DATA-05's whole mechanism and PITFALLS.md §10's subject. Take the path as an argument and
resolve nothing: it arrives from `resolve_paths()` and `db.py` must not invent a default (Phase 2
D-06, binding — the human-typed unit will not be edited to match a new one). Do not `mkdir` the
parent: `/var/lib/creatorpulse/` is created during provisioning by hand, and an application-level
directory creation there fails under exactly the conditions it is meant to handle.

`UPSERT_METRIC` is the verified `INSERT ... ON CONFLICT (creator_id, source, metric_date) DO UPDATE
SET` statement, every value bound by **named** placeholder (`:creator_id`, `:source`,
`:metric_date`, `:followers`, `:views`, `:likes`, `:video_count`, `:is_live`, `:collected_at`) and
the update list assigning each metric column plus `collected_at` from `excluded`. Never build SQL by
string formatting or interpolation — the query text is a module-level constant and the values are
always parameters (T-03-01).

`upsert_metric(conn, record)`: raise `ValueError` when `record.creator_id` is empty, because the
sources deliberately return a blank id and a blank id would silently create a fourth phantom creator
that no UNIQUE constraint catches. Serialise `metric_date` with `.isoformat()` and `collected_at`
with `.isoformat()` — Python 3.12 deprecates sqlite3's implicit date and datetime adapters, so
converting explicitly is required, not stylistic. Pass the four metric values straight through: a
`None` binds as SQL NULL, which is the correct and only handling. Do not substitute a zero, a
sentinel, or a default for any `None` metric anywhere in this module.

`write_run_row(conn, started_at, finished_at, rows_written, failure_count)`: one parameterised
INSERT, both timestamps via `.isoformat()`. Commit inside `db.py` (both writers) rather than leaving
an open transaction for the caller to remember — a one-shot job with one writer has no reason to
batch, and an uncommitted `runs` row is exactly the evidence a dying run needs to leave behind.

heterogeneous adapters. The submodule import sits at the bottom of the file with `# noqa: E402`, as
the verified example has it. Note for whoever adds `sources/_retry.py` in 03-03: a source module
importing `creatorpulse.sources._retry` while `creatorpulse.sources` is still initialising resolves
correctly because it is a submodule import, but `_retry` must not import anything from the package

**`sources/youtube.py`.** RESEARCH.md's verified YouTube example, which was checked against

Then the normalization boundary, which is the single most important seam in the system and lives
here, once per source.

**Branch on the flag, never on the value. This is a hard rule, not a preference.** `fetch` reads
`statistics["hiddenSubscriberCount"]` FIRST. When it is `true`, `followers` is `None` and the code
never reads `statistics["subscriberCount"]` at all — not to validate it, not to log it, not to
compare it. When it is `false` or absent, `followers` is `int(statistics["subscriberCount"])`, and a
missing `subscriberCount` key *in that branch* is an undocumented absence and MUST raise per D-03's
second rule. The verified RESEARCH.md example is already this shape:
`followers = None if hidden else int(stats["subscriberCount"])` — a conditional expression, so the
`int()` call is never evaluated on the hidden path. Do not restructure it into a read-then-branch.

The reason the rule is non-negotiable rather than tidy: RESEARCH.md Pitfall Y1 says YouTube reports
the literal string `"0"` in that slot (the exact false zero PITFALLS.md §13 describes), but assumption
A1 is only MEDIUM confidence on *which* shape comes back — `"0"` present, or the key omitted. Under
this read order both shapes map to `followers = None` by construction, so the parser is correct either
way and no one has to find a channel that hides its count to prove it. Read the value first and the
omitted-key shape becomes a spurious `KeyError` on a legitimate privacy setting, which is exactly the
failure D-03 splits its two rules to avoid.

Read `viewCount` and `videoCount` with subscript access, not `.get()`,
so an API shape change raises a `KeyError` loudly instead of producing a row of NULLs under a
successful run (D-03 rule 2). Convert with `int()`, never `float()`. Set `likes=None` and
`is_live=None` — neither is exposed by this endpoint, and `COVERAGE.md` records why the endpoints
that would expose them are opted out. Set `creator_id=""`; the collector attaches the real id, which
keeps this module ignorant of the database schema entirely (ARCHITECTURE.md's Internal Boundaries —
a source module never imports `db.py`). `collected_at` is `datetime.now(UTC)`, per row.

Before reading `items[0]`, check for an empty `items` list and raise `ChannelNotFound` naming the
handle. A bogus handle returns HTTP 200 with an empty collection, not a 404 (D-18, Pitfall Y2), and
without this the deliberate-failure proof in ROADMAP criterion 3 would be recorded as a success.
Call `response.raise_for_status()` before touching the body. No retry wrapper yet — SRC-05 lands in
03-03 and wraps this same `requests.get` call site without changing this function's signature.

**`collector.py`.** RESEARCH.md Pattern 3's orchestration shape.
`collect_once(conn, creators) -> RunResult`. Compute `metric_date = datetime.now(UTC).date()` and
`started_at = datetime.now(UTC)` once, before the loop, and thread `metric_date` into every fetch —
this is RUN-05 and it is why a run slipping past midnight cannot split across two dates. Iterate
creators in list order and each creator's `sources` map in its own order, so the journal reads in the
same order as the file. For each pair, look the fetcher up with `FETCHERS.get(source_name)`; a `None`
result is the D-09 skip — one `logger.info` line naming the creator and the source and a reason
token, then continue, neither a row nor a failure (D-10). Otherwise call the fetcher, attach the
creator id with `dataclasses.replace(record, creator_id=creator.id)` so a blank id never reaches the
database, call `upsert_metric`, and increment `rows_written`. After the loop, take `finished_at` and
call `write_run_row`, then return the `RunResult`.

The per-pair `try`/`except` boundary, the failure counter, and the try/finally that guarantees the
`runs` row on a mid-run raise are 03-05's work — this task's loop is the happy path and the skip
path. The orchestrator must contain **no** HTTP knowledge, no status codes, no `requests` exception
types, and no retry logic, now or later: that is ARCHITECTURE.md Anti-Pattern 1 and D-13, and the
easiest way to violate it is to "just add one small retry here."

  inside the process. Recorded as unresolved rather than assumed safe. Phase 7's `/status` staleness

  00:00:04 UTC keeps one date, correctly; but the *same* wall-clock day then has its rows filed
  under the previous UTC date, one second before the boundary. This is the intended behaviour and
  the reason RUN-05 exists, and it is called out here so a future reader does not "fix" it into
